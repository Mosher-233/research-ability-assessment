# 第三章 系统需求分析与总体设计

本章基于第一章的研究目标定位和第二章的理论技术基础，对大学生研究能力评价AI Agent系统进行全面的需求分析和总体架构设计。首先梳理系统的功能性和非功能性需求，然后设计系统的五层总体架构，最后重点阐述多智能体系统的架构方案和协作流程。

---

## 3.1 系统需求分析

### 3.1.1 功能性需求

本系统的核心业务闭环为"任务发布→证据收集→AI评价→报告生成"，围绕教师和学生两种用户角色展开。以下从六个功能模块分别描述需求。

**（1）用户管理。** 系统支持教师和学生两种角色的注册与登录。教师通过邮箱和密码注册账号，登录后可管理个人信息。学生同样通过邮箱注册登录。系统基于JWT实现无状态的身份认证——登录成功后颁发令牌，后续请求携带令牌完成身份验证。令牌中包含user_id和role两个关键信息，用于接口的权限控制。

**（2）任务管理。** 教师可以创建评价任务，填写任务名称（如"智能垃圾分类系统——图像识别算法研究"）、任务描述、起止日期等基本信息。创建完成后，教师可将任务分配给班级中的多名学生——通过从学生列表中选择目标学生完成分配。系统支持任务状态的自动流转：未开始的显示为"active"，所有学生提交完毕的标记为"completed"。教师可以查看每名学生在各任务下的完成进度百分比。

**（3）证据管理。** 学生可针对被分配的任务提交研究过程证据。证据分为两种类型：文本证据——学生直接在系统中输入研究过程的文字描述，如文献检索笔记、实验设计思路和数据分析记录；文件证据——学生上传PDF、Word等格式的研究文档副本。系统对学生提交的证据进行存储和管理，学生可以查看、编辑和删除自己提交的证据。

**（4）AI自动分析。** 这是系统的核心智能功能，采用LLM优先、规则兜底的双模策略。证据分类与等级评定优先通过EvidenceAgent调用LLM——LLM对照四级Rubrics量规对证据进行语义级KBM归类和等级评定，输出分类依据（rationale）。能力推理环节由InferenceAgent主导——将按维度分组的完整证据上下文与Rubrics量规发送至LLM，LLM逐维度评分并引用证据原文作为判据，返回包含evidence_quotes的结构化评分结果。系统自动从LLM推理中提取evidence_quotes，匹配对应证据记录，创建EvidenceCitation引用记录存入数据库。当LLM不可用时，系统自动降级至LogicUnit规则化计算（KBMLevel × 20 → 维度平均 → 四维度等权重加权）。对于文件证据，`pkg/extractor`包提供PDF、DOCX、TXT、Markdown等常见学术格式的自动文本提取。

**（5）报告生成。** 系统可生成面向学生个人的评价报告和面向教师的任务汇总报告。学生报告包含：综合得分和等级、四个维度的详细评分、以雷达图呈现的能力画像、优势维度与待提升方向的具体分析、个性化改进建议。教师报告在学生报告的基础上增加了班级统计维度——各维度班级平均分、学生排名和百分位、班级等级分布等。

**（6）知识图谱可视化。** 系统将学生的评价结果存储到Neo4j图数据库，以"学生→维度→得分"的图结构呈现能力的结构化关系。前端通过API获取图谱数据，使用可视化组件展示学生与各能力维度之间的得分关联。

### 3.1.2 非功能性需求

**性能需求。** 单名学生的全流程评估时间（从获取证据列表到生成综合报告）应控制在30秒以内——其中主要耗时在LLM API的调用上（批量测试平均2.03秒/次，完整评估接口含HTTP开销约12.6秒/次，n条证据共n+1次调用）。系统应支持至少10名教师同时在线操作和50名学生的并发访问。不涉及LLM调用的常规API接口（如登录、查询任务列表）的响应时间应控制在2秒以内。

**安全性需求。** 用户密码使用bcrypt算法（cost=10）进行哈希加密后存储，系统从不以明文形式存储或传输密码。DeepSeek API Key等敏感配置信息通过操作系统环境变量管理，不直接写入代码或配置文件。系统实现基于JWT的Bearer Token认证机制，所有受保护的API接口均需要验证请求头中的令牌有效性。遵循最小权限原则——教师和学生角色拥有不同的接口访问范围，学生无法调用教师的专属接口。

**可扩展性需求。** LLM客户端设计为OpenAI Chat Completions API兼容接口——通过修改配置文件中的base_url字段，系统可以在DeepSeek、OpenAI GPT-4、通义千问等不同LLM服务之间灵活切换，无需修改任何业务代码。数据库层面同时支持MySQL和PostgreSQL两种关系型数据库——通过配置文件中的database.type字段切换。系统采用分层架构设计（Handler → Service → Agent → Repository），各层之间的接口明确，便于独立替换或升级某一层的组件。

**可用性需求。** 系统在设计上实现了对两个非核心依赖的优雅降级。当Redis缓存服务不可用时，系统自动跳过缓存操作，改为直接查询数据库，缓存相关功能静默降级但核心评估逻辑不受影响。当LLM API调用超时或返回错误时，系统向上层返回明确的错误描述，不会导致整个服务的崩溃。前端额外支持基于Mock Token的离线演示模式，可以在不启动后端服务的情况下独立展示前端界面和交互流程。

## 3.2 系统总体架构设计

### 3.2.1 架构设计原则

系统的总体架构设计遵循以下四条原则：

**分层解耦。** 将系统垂直划分为表现层、网关层、业务逻辑层、数据访问层和基础设施层五个层次。每一层只依赖其直接下层，不感知更底层的实现细节。这种单向依赖的设计降低了系统各部分的耦合度，使层与层之间可以通过接口约定独立演进。

**Agent专业化。** 在业务逻辑层内部，进一步将评估任务的不同环节分配给不同职责的专业Agent——证据收集由EvidenceAgent负责，推理评分由InferenceAgent负责，反馈生成由FeedbackAgent负责。Agent之间的专业化分工使得每个Agent的实现逻辑清晰而聚焦，且可独立替换或升级。

**配置驱动。** 系统通过YAML配置文件管理运行环境的所有差异——数据库连接信息、LLM Provider和API Key、Redis连接信息、服务端口等。配置文件中可以使用`${ENV_VAR}`语法引用环境变量，实现敏感信息的隔离。

**优雅降级。** 非核心依赖的不可用不应导致系统整体不可用。Redis缓存不可用则跳过缓存，LLM API超时则返回错误而非崩溃——系统在关键路径上保持健壮性。

### 3.2.2 系统层次架构

> 【图3-1：系统总体架构图 — papers/figures/fig3-1-system-architecture.drawio】

系统采用五层架构，从顶至底依次为：

**表现层（Presentation Layer）。** 基于Vue 3和TypeScript构建的单页面Web应用（SPA）。使用Element Plus组件库提供统一的UI风格和交互体验，通过ECharts 6实现能力雷达图、班级对比柱状图等数据可视化。前端通过Axios HTTP客户端发送RESTful API请求与后端通信。

**网关层（Gateway Layer）。** 基于Gin框架构建的HTTP API网关，负责路由分发和请求预处理。该层的三个中间件——CORS中间件（处理跨域资源共享）、Logging中间件（记录请求日志）和Auth中间件（JWT身份认证）——在请求到达业务逻辑层之前完成通用处理。

**业务逻辑层（Business Logic Layer）。** 系统的核心层，采用Handler→Service→Agent三层嵌套结构。Handler负责HTTP请求的参数解析、输入校验和响应封装。Service封装跨模块的业务逻辑，如用户认证、任务管理、证据管理等。Agent层是本系统的智能核心——由ControlUnit作为编排中心，调度EvidenceAgent、FeedbackAgent、InferenceAgent、LogicUnit和StorageUnit协作完成评估任务，并调用LLM Client与外部大语言模型API进行通信。

**数据访问层（Data Access Layer）。** 封装了对关系型数据库和图数据库的数据操作。MySQL操作通过GORM ORM框架实现，提供类型安全的数据库查询接口。Neo4j操作通过官方Go Driver实现。Repository模式将数据操作抽象为独立接口，业务层通过依赖接口而非具体实现来调用数据操作——这使得更换数据库类型或调整数据库访问逻辑时只需要修改Repository层，业务层代码无需变更。

**基础设施层（Infrastructure Layer）。** 包含系统运行所依赖的外部服务和基础组件：MySQL 8.0关系型数据库存储所有结构化业务数据（用户、任务、证据、推理结果、报告）；Neo4j 5.23图数据库存储学生-维度-得分的图谱关系；Redis缓存服务加速高频查询；DeepSeek LLM API提供外部智能推理能力；Docker Compose实现所有基础服务的容器化编排和一键部署。

系统技术选型是在综合考虑性能需求、开发效率和可维护性的基础上做出的决策。表3-1列出了各项核心技术的选择方案、备选方案和选型理由。

## 3.3 多智能体系统架构设计

### 3.3.1 总体Agent架构

> 【图3-2：多智能体架构图 — papers/figures/fig3-2-agent-architecture.drawio】

本系统的多智能体架构采用主控-从属（Master-Slave）模式。ControlUnit作为主控Agent，承担评估流程的全局编排职责。五个专业Agent/单元作为从属模块，各司其职：

- **ControlUnit（控制单元）。** 评估流程的编排引擎。接收来自Handler层的评估请求，按照预设的5阶段流程依次调度各Agent，管理任务状态进度，整合评分和反馈结果，最终返回完整的EvaluationResult。ControlUnit持有各Agent和Service的引用，在流程中扮演唯一协调者的角色。

- **EvidenceAgent（证据Agent）。** 负责证据的收集、预处理和LLM优先的自动分类。通过EvidenceService查询指定学生在指定任务下的所有已提交证据记录。对于新提交的证据，自动调用LLM进行语义级KBM分类与等级评定（LLM不可用时降级为关键词匹配），返回附带分类依据（rationale）的结构化证据列表。

- **InferenceAgent（推理Agent）。** 负责能力推理与评分计算。采用LLM优先、规则兜底的双模策略：（1）主路径——调用`inferWithLLM()`，将按维度分组的完整证据上下文与Rubrics量规发送至LLM，要求LLM逐维度评分并引用证据原文作为判据（evidence_quotes），返回包含各维度得分、等级、评分理由和原文引用的结构化JSON；（2）降级路径——LLM不可用时自动回退至LogicUnit规则化计算（KBMLevel × 20 → 维度平均 → 四维度等权重加权）。LLM推理结果经解析后，自动从evidence_quotes字段匹配对应证据记录，生成EvidenceCitation引用链。

- **FeedbackAgent（反馈Agent）。** 负责诊断性反馈的生成。接收InferenceAgent的评分结果，调用LLM API生成面向各维度的改进建议和可操作的行动项。当LLM调用失败时，自动降级至预定义的规则化反馈模板，确保系统在任何条件下都能返回有意义的反馈输出。

- **LogicUnit（逻辑单元）。** 纯计算组件。提供证据评分（KBMLevel × 20 → 百分制）、维度得分计算（证据分数的算术平均）和综合得分计算（四维度0.25等权重加权平均）三个方法。

- **StorageUnit（存储单元）。** 封装对MySQL和Neo4j的数据操作。负责推理结果的持久化存储和图谱关系的更新。

### 3.3.2 Agent协作流程设计

> 【图3-3：Agent协作序列图 — papers/figures/fig3-3-agent-sequence.drawio】

完整的评估流水线分为以下五个阶段，每个阶段由ControlUnit统一调度：

**Stage 1 — 接收评估请求与状态初始化。** 当教师或学生通过前端的"生成评估"按钮触发评估时，Handler层调用Service层，最终将评估请求（携带studentID和taskID两个参数）传递给ControlUnit的ExecuteEvaluation方法。ControlUnit将任务状态标记为"processing"，进度初始化为0。

**Stage 2 — 证据收集与LLM主导评分。** ControlUnit调用InferenceAgent的InferAbility方法。InferenceAgent首先通过EvidenceAgent收集该学生在任务下的全部证据，然后按KBM维度分组。主路径：调用`inferWithLLM()`，将分组证据上下文与完整Rubrics量规作为提示词发送至LLM——LLM逐维度评分（0-100分），引用证据原文作为判据（evidence_quotes），返回结构化JSON。降级路径：LLM不可用时调用LogicUnit——每条证据KBMLevel × 20 → 维度内算术平均 → 四维度等权重（各0.25）加权综合得分 → GetLevelFromScore等级判定。系统自动从LLM推理中提取evidence_quotes生成CitationInfo列表。进度更新至50。

**Stage 3 — 结果持久化与图谱更新。** ControlUnit通过StorageUnit的StoreInferenceResult方法，将推理结果（综合得分、各维度得分JSON、等级、推理依据）写入MySQL的inference_results表。随后遍历各维度得分，通过UpdateKnowledgeGraph方法向Neo4j更新该学生的Student-Dimension得分图谱关系。进度更新至70。

**Stage 4 — LLM辅助反馈生成。** ControlUnit调用FeedbackAgent的GenerateFeedback方法，将评分结果（各维度得分、等级、推理依据）作为上下文输入，请求LLM生成面向各维度的诊断性改进建议——包含当前得分、目标得分、具体建议和可操作的行动项（ActionItems）。当LLM API调用失败（网络超时或服务异常）时，系统自动降级至generateRuleFeedback方法，根据各维度得分区间从预定义的规则模板库中选取对应的反馈文本。进度更新至90。

**Stage 5 — 评估完成标记。** ControlUnit将任务状态更新为"completed"，进度标记为100%，构建包含评分结果和反馈内容的完整EvaluationResult，返回给上层Handler。

### 3.3.3 消息传递与数据流设计

> 【图3-4：评估数据流图 — papers/figures/fig3-4-data-flow.drawio】

系统内部的数据流从原始证据开始，经过多轮Agent处理后逐步转化为结构化的评价结果，整个转化过程可以分为五个阶段：

**阶段一：原始证据（输入）。** 文本证据或文件证据，内容为学生提交的研究过程记录——可能包含自然语言描述的文献检索策略、实验设计思路、数据分析过程和结论。

**阶段二：预处理证据。** 经过EvidenceAgent清洗和格式化后的规范文本——不必要的空白和特殊字符被移除，文本长度被控制在2000字符以内。

**阶段三：证据反馈。** 经过FeedbackAgent评估后的结构化反馈——以JSON结构包含KBM级别（1-4）、证据优点、不足、改进建议和总体评价。每条反馈与原始证据通过evidence_id一对一关联。

**阶段四：推理结果。** 经过InferenceAgent综合推理后的四维度评分——包含每个维度的得分（0-100分）和对应的推理依据文本。推理结果存储为inference_results表中的一条记录。

**阶段五：综合报告。** 经过ControlUnit整合后的完整评价报告——包含等级判定、班级对比、优势维度分析、改进建议和雷达图源数据。报告以JSON格式存储在reports表中，前端通过API获取后渲染为可视化页面。

整个数据流中，所有中间结果在Go Agent之间以强类型结构体的形式传递，避免了类型错误和数据丢失。最终的持久化结果以JSON格式存储在MySQL中，保证了存储结构的灵活性和可扩展性。Neo4j中以图结构存储学生-维度-得分关系，为图谱可视化提供高效的查询接口。
